## 二、项目职责与 Core 边界（MUST）

1. **Nodus CLI 是面向 Linux 服务器的节点部署与运维工具。** 主要部署对象为代理节点、Nodus 节点和 Tailscale 节点。CLI 负责安装、部署配置、进程启停、本地状态查询、诊断，以及这些操作所需的权限与系统适配。涉及 Nodus Core 的部署由 CLI 承担 Linux 宿主职责，包括信号处理、本地控制、受管文件、预算传入及结果呈现。部署能力按已批准的阶段和权限范围实施。
2. **CLI 只实现部署与运维所需的宿主逻辑。** Nodus 的协议处理、路由与规则决策、DNS、连接及会话语义、资源计量、业务配置校验与运行态提交由 Nodus Core 的公开 Rust 接口执行。Tailscale 节点的业务行为由该节点所用的运行组件负责。CLI 可以校验部署参数、路径和权限，编排操作并传递输入和输出。禁止在 CLI 实现、复制或补写节点业务逻辑、访问 Core 内部状态、填造业务结果或静默降级。依赖未提供所需能力时，返回明确的不可用结果。
3. 新增命令、模块或依赖时，必须说明服务的节点部署或运维场景。涉及节点业务的命令还须说明实际调用的公开接口和 CLI 承担的宿主步骤。禁止以 App 的功能清单或交互作为 CLI 的移植目标、功能对齐要求或验收依据。展开后续阶段、增加命令或登记 TODO 均不得扩大项目职责。职责变更须由用户明确确认，并先更新本章，再实施。
4. 维持单个 `nodus` 二进制。进程启动入口完成装配，命令层处理参数与呈现，守护进程协调请求，Core 接入层将宿主意图转换为受约束的 Core 调用。离线命令复用适用的 Core 校验入口。仅在有实际调用者或需要隔离现有职责时拆分模块。
5. 使用 Rust Edition 2024，并在本仓库 Rust crate 禁止 `unsafe`。平台调用使用有安全接口的依赖。通过 `Cargo.lock` 与依赖声明固定可追溯的 Core 来源、版本或提交及所需 features；本地路径联调须记录来源提交及是否含未提交改动，正式构建须能从干净检出重现依赖来源。新增依赖前核对实际用途和 Linux 目标兼容性，许可准入遵循[《依赖与许可证规范》](依赖与许可证规范.md)。
6. 启动时从显式启动参数或部署配置取得预算，记录限额的对象、单位、来源及超限行为，经 Core 校验并完整传入。缺失必要预算、单位非法或溢出时启动失败。任何有效默认值与新硬上限应有已确认的依据；CLI 不擅自用无限额度、静默截断或另建业务预算替代 Core 契约。展示时区分 Core 计量与进程 RSS。

### 节点部署与运维生命周期

以下职责适用于本项目已接入或按阶段接入的节点类型，以单台 Linux 主机上的指定节点实例为操作对象。

1. **部署前检查。** 变更主机前，检查适用的系统及架构、运行组件版本、服务账号、配置及数据目录、权限和所需端口。已有部署时，确认实例与受管对象的归属，并区分新装、已有相同部署和冲突。相同部署参数重复执行应给出可预期的结果，保留已有用户资产。
2. **部署验收。** 分别确认安装完成、服务启动和节点就绪。依据运行组件实际报告的状态或已授权的探测确认就绪。仅确认进程启动时只报告该阶段。就绪失败或暂无法确认时，记录实际状态及原因。守护进程自身的就绪条件遵循[《守护进程与本地控制规范》](守护进程与本地控制规范.md)。
3. **升级与回滚。** 升级前核对目标版本、产物来源及配置兼容性，保留可恢复的上一版本与部署配置。升级失败时按可恢复范围执行回滚，报告原始失败、回滚结果、当前实际运行的版本与状态。保留已有节点身份、密钥和用户数据。
4. **卸载与资产保留。** 卸载时先确认并停止目标实例，再按归属清理该实例的受管服务单元和部署文件。默认保留节点身份、密钥和用户配置。彻底清除须由用户显式指定，并限定在目标实例及已授权资产范围内。共享或归属无法确认的对象保留并报告。
5. **部署身份与归属。** 每个部署实例必须能唯一定位其受管服务、配置目录、数据目录和适用的控制端点。同一主机存在多个实例时，重启、升级、回滚和卸载必须确认目标实例，并限定在该实例的受管范围内。
6. **运维诊断与自动化。** 提供目标实例的版本、服务状态、最近一次可观测的操作结果及脱敏诊断。保留运行组件返回的错误原因，明确区分失败与结果未确认。供脚本使用的 JSON、退出码与兼容承诺遵循[《命令行与输出契约》](命令行与输出契约.md)和[《错误代码规范》](错误代码规范.md)。

## 三、配置文件和编程边界

1. CLI 负责其受管配置、资源和目录的定位、权限核验及显式文件操作。向 Core 交付已授权的绝对路径和必要的只读资源引用。来自配置正文、订阅或 IPC 的路径不得自行扩展文件访问范围。外部输入文件保持只读，除非命令明确授权修改其目标。由 CLI 管理的持久化替换使用同文件系统的原子发布，并按承诺处理同步、权限和失败。
2. 将参数解析、输入校验及结果转换与 I/O 分开。默认最小可见性，模块通过明确接口协作。状态、单位及错误使用能表达语义的类型；生产路径将无效输入和可恢复失败作为正常错误返回，避免以 `unwrap`、`expect` 或 panic 代替处理。
3. 活动任务、Socket、文件和共享状态须有明确所有者。同步锁不得跨异步等待或阻塞 I/O。说明资源的作用域、停止入口和释放完成条件，取消等待不能提前释放仍被实际工作使用的资源。守护进程的具体契约见[守护进程与本地控制规范](守护进程与本地控制规范.md)。
4. 使用 Rust 格式化约定。清除本次涉及且已确认无生产用途的代码，核查受支持目标及公开入口后再删除。公开行为变更同步帮助、契约和受影响的使用示例。

### 最简实现（MUST）

- 新增或修改功能时，实施方必须先明确验收条件和仍适用的契约，核对已有可复用的入口，再选择直接满足这些条件的实现路径。
- 新增中间文件、快照、格式转换、重复读写、额外状态或抽象层时，必须逐项说明对应的需求或已核实的约束、可核对的依据，以及省略后哪个实际场景无法满足验收条件。缺少具体依据的步骤不得引入。
- 实现路径须保留适用的命令契约、实例归属、权限、幂等及失败恢复行为。涉及节点业务时沿用第二章规定的公开接口和职责边界。

## 四、注释与文档注释

1. 说明性注释用中文，保留准确的 Rust、Linux 和协议术语。用 `//!` 说明模块职责、边界与主要调用关系；用 `///` 记录公开接口及具有调用约束的内部接口；用 `//` 解释局部实现中的设计原因。为有助于理解的内容写注释，避免逐行复述代码。
2. 接口文档按实际影响说明输入前提、成功条件、失败后果及副作用。命令和控制入口说明执行方式，以及返回时对应的是校验完成、操作已提交还是结果已确认生效。命令参数、退出码及 JSON 字段的完整契约见 [CLI.md](../CLI.md)，源码注释引用相关章节。
3. 文件与 Socket 权限、凭据、预算、并发及取消等关键约束写在对应实现附近。说明所有者、不变量、设计依据、由谁核验、何时生效以及失败后保留的状态。涉及预算交付时，分别写清 CLI 已完成的输入校验和 Core 实际接受的限额。
4. 接口、错误路径、权限或资源生命周期变化时，同步更新或移除受影响的注释。注释描述当前行为，阶段计划记入 [TODO.md](../TODO.md)，实测结果记入对应工作报告或验证证据。注释和示例使用脱敏数据，禁止记录凭据、私钥、令牌或真实用户数据。
